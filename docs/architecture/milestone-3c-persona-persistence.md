# Milestone 3C — Persona Persistence and Database Integration

**Status:** Decisions approved. `001`-`003` were reported executed in the development project (tracker updated on that report), and the first hosted integration run found one **runtime blocker** in the deployed SQL: stale-version conflicts hang (section 10). A forward fix, `004`, is authored and **pending review; it has not been executed**. The Supabase repository is wired and works, but the application stays on the in-memory fixture by default (`PERSONA_STORAGE=fixture`) and **must not be switched to `supabase` for real use until `004` is executed and verified**.

For the reviewer: start with [docs/sql/milestone-3c/REVIEW.md](../sql/milestone-3c/REVIEW.md).

## 1. Goal and boundaries

Replace the in-memory Persona repository with durable, account-isolated Supabase persistence, without changing the screens, service layer or workflows. The application keeps using the authenticated Supabase session (`createAuthenticatedClient`), PostgREST carrying the user's JWT, and PostgreSQL RLS for isolation. There is no service-role key, no direct PostgreSQL connection and no custom runtime role, and a boundary test enforces that.

### Two additional requirements (applied)

1. **Each mutation RPC returns the resulting Persona state, with the updated version, from inside the same transaction.** Every mutation except `persona_delete` returns `jsonb` built by the read-only `persona_detail_json` as its last step, in the same shape the application reads with one select (children, revision count, version). The repository parses it directly: **one request per mutation, no second read.** `persona_delete` returns the deleted id. This adds one function (`persona_detail_json`, read-only, owner-scoped, `SECURITY INVOKER`, not on the gate allowlist), bringing the package to 11 functions.
2. **Atomicity is verified for creation, bulk operations, revisions and default changes** (section 6).

## 4. Repository integration

`SupabasePersonaRepository` implements the same `PersonaRepository` the service already uses; the fixture is unchanged and remains for isolated tests.

- **Identity:** the session callback supplies the verified user id. A different `accountId` is "not found" with no database call. Reads also filter `account_id` explicitly in addition to RLS. No RPC has an account parameter (a test enforces this).
- **Mutations:** exactly one RPC and one request each. The returned state is parsed with Zod and mapped to `PersonaDetail`; a missing or malformed state is a `PersonaPersistenceError` carrying only a code.
- **Reads:** one PostgREST SELECT on `personas` with embedded children.
- **Contract checks:** the nine RPC names in `PERSONA_RPC` equal the SQL gate allowlist, and every parameter the adapter sends equals the declared SQL signature (both tested).
- **Selection:** `PERSONA_STORAGE` (server-side, default `fixture`).
- **Master Identity:** only the read-only `findProfile`; Persona TypeScript never references `identity_profiles` or `accounts`.

## 5. Mutation-to-RPC mapping

See [REVIEW.md §3](../sql/milestone-3c/REVIEW.md). Summary: create → `persona_create_with_configuration`; details → `persona_update_metadata`; field toggle, field move, bulk action and presentation save → `persona_apply_profile_field_changes`; section show/hide/rename → `persona_upsert_section`; section move → `persona_reorder_sections`; default → `persona_set_default`; archive/restore → `persona_set_lifecycle`; duplicate → `persona_duplicate`; permanent delete → `persona_delete`.

## 6. Atomicity verification

Established in three layers; the last has **not** been run.

- **By construction (static, runs now).** Each RPC is one function = one transaction. Tests assert: no `COMMIT`/`ROLLBACK`/`SAVEPOINT`/`EXCEPTION`/dblink/background/network call in any function; validation (22023) precedes the first write in create; write order for create (Persona, selections, overrides, sections, default switch, revision) and for default changes (advisory lock, clear and revise the previous default, set and revise the new one); one version bump and one revision after the batch loop with nothing written after the revision; every revision carries the version of the row it describes and is the last write; the returned state follows the last write.
- **Failure injection (fixture contract, runs now, `tests/persona-atomicity.test.ts`).** A failure at the revision insert leaves no part of the mutation: no Persona or children from a failed create (including its default switch), no field change or version bump from a failed batch, both Personas untouched when either default-change revision fails, an archived default stays default when its revision fails. This proves the contract the application relies on, not PostgreSQL.
- **Hosted runtime (authored, not run).** A failed create and a failed batch leave nothing; a created Persona has 7 selections, 9 sections and exactly one revision; concurrent default switches leave one default and no torn revisions; revision numbers are `1..version` for every Persona; deletion purges only the deleted Persona's rows; returned state equals a fresh read after every mutation.

Limit: atomicity inside PostgreSQL is established by construction and not yet executed; no test injects a failure _inside_ a PostgreSQL function because that would need a `postgres`-written fixture (declined under D-7).

## 9. Known limitations and open items

- The SQL is **syntax-checked only** (98 statements and 18 function/`DO` bodies parse with the PostgreSQL grammar). Column names, types and runtime behaviour are unverified until it runs.
- Deleting a Persona purges that Persona's revision history (D-2).
- The `accounts` anchor insert (D-8) is the one place a Persona function writes an M2 table.
- **No quota for the MVP (D-5): revisit before public launch.**
- `persona_update_metadata` takes a slug parameter the application does not use; the adapter passes `null`.
- `persona_detail_json` is callable as a read-only RPC returning only the caller's own data.
- GraphQL behaviour is unverified until the hosted test runs (D-3).

## 10. Milestone 3D runtime findings (first hosted integration run)

Run against the development project with the two dedicated RLS test accounts, the anon key only, no service role and no database connection. Test Personas were created with unique names and removed afterwards (both accounts verified clean).

### F-12 BLOCKER: a stale version never returns (SQLSTATE 40001)

| Probe                                      | Result                                  |
| ------------------------------------------ | --------------------------------------- |
| Stale expected version (SQLSTATE `40001`)  | Request never returned: aborted at 20 s |
| Foreign Persona (`P0002`)                  | HTTP 500 in 162 ms, correct `code`      |
| Delete of a non-archived Persona (`55000`) | HTTP 500 in 237 ms, correct `code`      |

Every stale-version call hung: through the adapter, and through a raw `POST /rest/v1/rpc/...` with no adapter. This is consistent with the platform treating `40001` as retryable and re-running a request that fails deterministically; it is **not confirmed from platform logs**. Either way a stale version is an ordinary user event, so it must not be signalled with `40001`.

**Proposed resolution (D-9, needs approval):** `docs/sql/milestone-3c/004-persona-version-conflict-sqlstate.sql` redeploys only the seven functions that check an expected version, changing only the stale-version SQLSTATE to `PT409` (verified mechanically: each is byte-identical to its `003` definition apart from that literal). No table, policy or grant changes; privileges and settings are asserted unchanged before `COMMIT`. The application already maps `PT409` (and still `40001`) to `version_conflict`, and `PERSONA_ERROR_SQLSTATE.version_conflict` is now `PT409`. Rolling back to `40001` is not a safe recovery.

**Impact until `004` runs:** a stale version through the Supabase adapter hangs that request. Hence the storage default stays `fixture`. Four hosted tests that depend on it are gated by `FOLIOONE_PERSONA_004_EXECUTED=1` and are reported as blocked, not hidden: they must pass once `004` is executed.

### Reads and error handling changed in 3D

- Single-Persona reads now use `persona_detail_json` (owner-scoped, NULL when missing or foreign); lists use one select with embedded children. Both work against the real database.
- PostgREST JWT errors (`PGRST301/302/303`) map to the signed-out state.
- Mutations are never retried (tested), so a possibly committed write is never re-sent.
